# JAN検索のリソース制限

`GET /api/products/{jan}` は、認証・認可後、外部サービスを呼ぶ前に429で要求を拒否します。待機キューはありません。

| 設定キー | 既定値 | 意味 |
| --- | ---: | --- |
| `JanSearch:Limits:PerUserPerMinute` | 10 | oid（なければNameIdentifier）ごとの1分固定窓上限。レプリカ単位 |
| `JanSearch:Limits:TotalPerMinute` | 120 | 最大レプリカ数に配分する予算 |
| `JanSearch:Limits:MaxReplicas` | 10 | Container AppsのmaxReplicas以上に設定する値 |
| `JanSearch:Limits:ConcurrentRequests` | 4 | JAN要求の同時実行上限。レプリカ単位 |

各レプリカの固定窓上限は `TotalPerMinute / MaxReplicas` の切り捨てです。既定では12要求/分/レプリカです。既存IaCの最大10レプリカを前提に保守的に配分し、単一レプリカでも上限を緩めません。固定窓の境界には通常のバーストがあり、再起動でカウンターが初期化されます。月間の課金上限や厳密な分散クォータを保証するものではありません。最大レプリカ数を増やす場合は、この設定も同時に更新してください。環境変数では `JanSearch__Limits__MaxReplicas` 等を使用します。

成功結果は5分、商品なしは30秒キャッシュします（最大256キー/レプリカ）。同時のキャッシュミスを直列化して、同じJANの検索をまとめます。失敗はキャッシュしません。上流429は即座に再試行せず、Retry-After（未指定時60秒、1〜300秒）に従って、レプリカ内の全JANで外部呼び出しを停止します。キャッシュ済み結果は引き続き返せます。クライアント向け429にもRetry-Afterを付けます。

分散キャッシュ等の追加サービスは使用しません。実際の外部API契約に合わせて予算を調整し、上流429と使用量を監視してください。
